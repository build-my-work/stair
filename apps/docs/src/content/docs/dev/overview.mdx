[工作台命令契约](/dev/workbench-commands/)、[持久化](/dev/persistence/)、

> **增量适用原则**：这些约束约束新增和正在修改的代码，不要求为统一形式专项重构存量；
> 但每条不变量对任何触碰它的改动都必须保持。

## 不变量

1. **面板身份不进领域模型。** Panel ID 只是展示状态；Session、Project File、Drawnix 能力的路由一律由 Session 的不可变 `projectId` 决定。把面板位置当业务身份用（"左栏""右栏"）是结构性错误。
2. **命令层是布局的唯一写入口。** UI 组件不得直接修改 Workbench atom；每条命令必须声明影响哪个 Project、`auxiliary.length` 变化量、Focus 结果和失败结果。通用 `navigate()` 内部不得隐藏布局修改。
3. **普通导航不新增面板。** 目标已可见则聚焦，否则替换 Primary；只有显式命令（New Session in Panel、Branch、Open in New Panel、presentBrowser）才创建 Auxiliary。文件预览走可复用的 Preview，永不提升为 Primary。
4. **Workspace → Project → Session 所有权始终成立。** Session 从创建起携带不可变 `projectId`；跨 Project 内容不可见、不可选、不可写——UI 不提供入口，服务端对构造请求仍拒绝。
5. **只持久化语义描述符。** 布局文档存"什么在哪"，不存 React 状态、原生 Runtime ID 或 reveal intent；Browser Runtime 必须可由描述符重建。
6. **引用是唯一的跨内容协议。** 文本、EPUB、PDF、网页、聊天选区生成同一个 `Reference` 值；草稿、消息、Add Note、模型输入与 reveal 消费它，各内容模块不各自实现写入协议。

## Review 清单

1. 这次改动有没有绕过命令层直接写布局状态？
2. 新增的领域字段是否携带 Project 归属？有没有可能跨 Project 读到？
3. 面板 ID 有没有渗进领域模型或服务端校验之外的地方？
4. 新增的持久化内容是语义描述符吗？Runtime 或组件状态有没有被序列化？

验证：改命令层至少跑 `workbench-commands.test.ts`、`workbench-layout.test.ts` 与 `typecheck`；
跨 Project 改动加跑 `project-communication.test.ts`、`default-project.test.ts`。
精确 test name 映射见 `docs/stair-full-regression.md` §19.1。
