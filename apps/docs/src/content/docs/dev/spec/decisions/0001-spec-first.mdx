> **状态**：已采纳（2026-11-03）

## 背景

Stair 的产品信息分散在重建方案、回归规范、竞品研究和学习科学整理中，没有一处能回答"Stair 是什么、为什么这样设计、有哪些模块、各自做到哪一步"。学习层即将开始建设，功能会快速增加，如果不先把意图写清楚，产品很容易变成功能堆砌。

## 决定

1. 在现有文档站 `apps/docs` 中新增面向用户的"产品介绍"（`/design/`，以功能页为主）和面向团队的"产品规格"（`/dev/spec/`，定位、原则、模块、流程与决策）。
2. 新功能先写功能页并标为"已规划"，再开始实现；状态随实现推进更新。
3. 功能状态写在功能页 frontmatter 中，功能看板和模块地图自动汇总。
4. 已交付的功能必须关联回归 Case，否则构建失败。
5. 内容按产品视角重写，不直接迁移原有研究文档；原文档作为原始材料保留在 `docs/` 下。

## 理由

- 规格和代码在同一个仓库，可以在同一个 PR 里修改，减少两者脱节。
- 用 frontmatter 记录状态而不是手写表格，看板永远和功能页一致。
- 与回归 Case 关联，让"已交付"有可检验的含义。
- 与现有文档站合并，不新增依赖和第二个站点，三类读者从同一个入口进入。

## 影响

- 新增 `/design/` 与 `/dev/spec/` 下的页面，以及 `src/design/catalog.ts`。
- 新功能的 PR 评审需检查对应功能页是否存在并已更新。
