## 为什么规格先行

先写功能页，逼着我们在写代码之前回答：这个功能服务哪个目标、落实哪条原则、怎样算做完。答不上来的功能不进入开发。

功能页和代码在同一个仓库，同一个 PR 修改。规格和实现不一致时，以代码和回归 Case 为准描述现状，并把不一致当作要修的问题。

## 一个功能的生命周期

<Steps>
1. **构思中（exploring）**：想法还没想清楚。可以只写场景和"还在想的问题"。
2. **计划中（planned）**：用户会经历什么、验收约定都写清楚了，可以排期。开 PR 新增或修改功能页，评审通过后合并。
3. **开发中（in-progress）**：实现 PR 开始时把状态改为开发中。行为有调整，在同一个 PR 里更新功能页。
4. **已上线（shipped）**：实现合并时改为已上线，并在 `cases` 中填上 `docs/stair-full-regression.md` 里的回归 Case ID。没有 Case 的功能不能标为已上线——构建会直接失败。
</Steps>

任何阶段都可以改为**不做了（dropped）**。不删除页面，在正文里写明原因，避免以后重复讨论。

## 功能页怎么写

产品介绍的结构是：一条学习主线 → 六个空间（首页、资料、学习、练习、实战、成长）+ 底座（工作台与 AI）→ 功能。功能页放在所属空间的目录 `apps/docs/src/content/docs/design/<空间>/` 下，文件名用英文短横线命名；空间清单见 `src/design/catalog.ts` 的 `SPACES`，每个空间目录的 `index.mdx` 是空间概览。不在空间目录下的功能页会导致构建失败。

新功能先回答"它属于哪个空间"。哪个空间都放不进去，说明它可能不该做，或者产品结构需要先讨论。

frontmatter：

```yaml
---
title: 先猜一下
description: 一句话说明这个功能（会显示在功能看板上）
status: planned        # exploring | planned | in-progress | shipped | dropped
module: learn          # 取值见 src/design/catalog.ts 的 MODULES
principles: [5]        # 主要落实的设计原则编号
cases: []              # shipped 时必填，如 [READER-01, EPUB-03]
---
```

读者只会在标题下看到状态；模块、原则和 Case 用于产品全景、[模块地图](/dev/spec/modules/)和构建校验，不展示给读者。

**功能页写给用户看。** 读者是一个想学东西的人，不是开发者。按这个顺序写，没有内容的小节可以省略：

| 小节 | 写什么 |
|---|---|
| 开场场景 | 一个具体的学习时刻：你在读什么、遇到了什么、Stair 做了什么。不用小标题 |
| 为什么这样做 / 这对你有什么用 | 用大白话讲道理，不引文献、不提证据等级 |
| 你会遇到的 | 用户能看到、能做的事，到"点什么、看到什么"这一层 |
| 常见问题 | 用户可能的疑虑，一问一答 |
| 给开发：验收约定 | 折叠在 `<details>` 里：可检验的条目、规则与边界、待讨论。上线时能对应到回归 Case |

写作约定：

- **第一段是一句定义加"它不是什么"**，例如「先猜一下是开讲前的一两个小问题。它不是摸底考试：不打分，猜错也有用。」然后才是场景。
- **用同一个贯穿例子**：学 TCP，起因是"视频会议总卡"。需要第二个主题做对比时，用"写作"。
- **容易混淆的功能写一节「和 ××× 有什么不同」**，帮读者在相邻功能之间做选择。
- **写一节「目前做不到的」**：诚实写出局限，尤其是 AI 可能出错的地方，以及读者可以怎么核对。
- 用"你"，不用"用户"。
- 不出现内部术语：Primary/Auxiliary、fingerprint、量规、支架、L1–L5、知识单元等只能出现在折叠区和产品规格中。
- 已上线的功能链接到对应的使用文档；计划中的功能不承诺时间。

## 设计决策怎么写

改变方向、在几个方案之间取舍、修订一条原则时，在 `dev/spec/decisions/` 下新增一篇，编号递增。格式：

- **状态**：提议 / 已采纳 / 已废弃（被哪一篇取代）
- **背景**：为什么现在需要做这个决定
- **决定**：决定了什么
- **理由**：证据和权衡
- **影响**：哪些原则、模块、功能要跟着改

决策一旦采纳就不再改写内容；要推翻它，新写一篇并把旧的标为已废弃。

## 新增模块

模块定义在 `apps/docs/src/design/catalog.ts`。新增模块要同时改本页的模块地图说明，并在决策里写明为什么现有模块装不下。

## 评审时问四个问题

1. 它补的是闭环中的哪一段：输入、加工、输出、反馈、记忆还是迁移？
2. 它让用户更早地自己动脑，还是只是生成了更多可以读的内容？
3. 它应该是一个新入口，还是由已有入口在合适的时候自动调用？
4. 它会留下什么证据，怎样和来源、AI 的帮助区分开？
