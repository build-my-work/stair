# Stair 阶段 0–4 功能一致性外部审查

请对当前仓库执行**只读审查**，禁止修改、创建或删除任何文件，也不要运行会改变 Git 状态的命令。

## 审查目标

用户只授权重写并理清代码架构，没有授权改变既有产品功能。请深度分析当前阶段 0–4 相比旧 Stair 产品是否出现了用户可感知的功能变化、功能丢失或交互回归。

请以 `git show <ref>:<path>`、`git diff` 和当前源码为证据；不要只根据计划文档推断。

## 审查范围

1. 阶段 0：运行时数据路径、窗口状态、日志与工作区/Session 新建行为。
2. 阶段 1：Workspace、Session、Provider 基础行为。
3. 阶段 2：Workbench、Panel、Sidebar、Navigator、焦点与布局行为。
4. 阶段 3：Project Files 的入口、位置、树、打开/刷新行为。
5. 阶段 4：EPUB/PDF 阅读、导航、正文布局、进度、选区、高亮、安全边界。

后续阶段尚未实现的能力也要列出，但必须与“已实现功能的回归”分开。例如 Add Chat、Add Note、引用、浏览器或白板若被计划推迟，应标为“延期造成的当前产品能力缺口”，不要误报为阶段 4 实现 bug。

## 已知待核实问题

当前 `ProjectFileEpubReader.tsx` 在导航打开时固定使用两列 Grid；旧版在窄容器中使用覆盖式导航。请核实根因、影响范围，并检查 PDF 是否有同类问题。

## 输出要求

请用中文输出，并按以下结构组织：

1. 按严重级别排序的发现，每项包含：分类、用户影响、旧版证据、当前证据、建议。
2. 功能一致性矩阵：旧版能力、当前状态、属于回归/显式延期/等价替换/安全收窄/无法确认。
3. 明确区分：
   - 会改变业务语义的数据或状态逻辑；
   - 只改变实现结构、但用户行为等价；
   - 当前确有用户可感知变化。
4. 指出计划文档与真实实现不一致之处。
5. 给出最小修复边界；如修复需要改变现有架构，请明确标注。

不要泛泛评论代码风格。所有重要结论尽量给出文件路径、函数或 JSX 区域作为证据。
